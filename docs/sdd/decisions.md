# Журнал архитектурных решений (ADR)

Формат унаследован от Autotargeting (docs/sdd/decisions.md).

---

## ADR-001: Rust-first — Python/C++ только по необходимости

- **Статус:** принято (требование заказчика, 2026-09-01)
- **Контекст:** bkb — Python (быстро итерировался, но монолит с дублированием,
  хрупкой синхронизацией через имена потоков); Autotargeting — Rust- workspace
  с 294+ тестами и C++ NPU-мостом.
- **Решение:** весь рантайм — Rust. C++ допустим только как фолбэк NPU-моста;
  Python — только разовые диагностики (v4l2-ctl, rknnlite-пробы).
- **Последствия:** сборка на борту медленнее (кроcс-компиляция не настроена),
  зато один язык, типобезопасность на границах, нет GIL, нет ABI-граблей D-008.

## ADR-002: In-process FFI к NPU вместо сокет-моста

- **Статус:** принято
- **Контекст:** Autotargeting гонял YOLOv8 через C++ rknn-bridge по Unix-сокету
  с base64-кадрами — 96 мс на раунд (D-015), потолок детектора ~10 FPS.
- **Решение:** собственный `crates/rknn-sys`: прямые extern-C байндинги к
  librknnrt.so, zero-copy через rknn_set_io_mem, инференс в потоке детектора.
- **Альтернатива:** тащить rknn-bridge как сабпроцесс — сохраняет 96 мс накладных.
- **Риски:** корректность FFI-структур — снята сверкой с официальным rknn_api.h
  (вендорится в крейте) и портированием логики 1:1 из проверенного rknn_model.cpp.

## ADR-003: NanoTrack на tract + два статических backbone

- **Статус:** принято
- **Контекст:** TrackerNano в OpenCV unavailable из Rust; ONNX Runtime (ort) на
  Debian 12 aarch64 не линкуется (D-008 из Autotargeting).
- **Решение:** tract (чистый Rust). Исходный ONNX backbone экспортирован со
  статическими формами входа 255×255; tract чтит их, OpenCV — игнорировал.
  Поэтому backbone пересохранён в двух статических вариантах: 127×127 (шаблон,
  `nanotrack_backbone_127.onnx`, формы пересчитаны onnx.shape_inference) и
  255×255 (поиск, оригинальный `..._sim.onnx`).
- **Замеры (x86 dev, release):** backbone127 4 мс + backbone255 14 мс + head 3 мс.
- **Фолбэк:** C++ OpenCV TrackerNano-бридж (не понадобился).

## ADR-004: Детектор = RKNN-модель bkb, layout с автоопределением

- **Статус:** принято
- **Контекст:** готовой .rknn под наш класс-набор нет; конвертация yolov8n.onnx
  требует rknn-toolkit2 на x86 Linux. У bkb есть полевые модели rk3588.
- **Решение:** `models/model_5_dynamic_rk3588.rknn` (5 классов — уточняется
  эмпирически, см. HARDWARE_TEST_RESULTS). Декодер сам определяет layout:
  6 выходов → ветки bkb (DFL, без sigmoid), 1 выход → голова Autotargeting
  (sigmoid по D-010). Динамическая форма входа — rknn_set_input_shapes(640).
- **Альтернатива:** конвертация yolov8n COCO на x86 — отложена (нет машины
  с Linux+x86 под рукой ночью).

## ADR-005: Гибрид C — правила слияния детекции и трекинга

- **Статус:** принято
- **Решение:** детекция каждые N кадров (по умолчанию 10) в отдельном потоке
  (NPU не блокирует трекинг). Выбор цели: (приоритет класса, IoU с текущим
  боксом, confidence). Реинициализация трекера на боксе детекции всегда
  (точнее трекера). Потеря: score < min_track_score `lost_patience` кадров
  подряд, либо бокс у края кадра → форс-детекция на следующем кадре.
  Стабилизация центра: скользящее среднее bkb (Stabilizer).

## ADR-006: Copy-mode инференс вместо zero-copy (rknn_set_io_mem)

- **Статус:** принято (2026-09-01, по факту железа)
- **Контекст:** ADR-002 предполагал zero-copy через DRM/GBM. На Radxa Debian 12
  (rknpu2 2.3.0) путь rknn_create_mem уходит в DRM_IOCTL_GEM_FLINK → EACCES →
  PRIME_HANDLE_TO_FD → SIGSEGV внутри librknnrt (strace в docs/syn.strace.txt).
- **Решение:** copy-mode: rknn_inputs_set (UINT8/NHWC) → rknn_run →
  rknn_outputs_get(want_float=1). Замер: 35.7 мс на инференс 640×640 —
  копирование буферов в этих 35 мс незаметно (NPU-прогон доминирует).
- **Последствия:** вернуться к zero-copy можно после апгрейда рантайма/ядра;
  интерфейс safe.rs менять не придётся (infer() инкапсулирует режим).

## ADR-007: Три FFI-подвоха rknn-sys (уроки падений на aarch64)

- **Статус:** принято (2026-09-01)
- **1. rknn_context = u64 на aarch64** (u32 только на 32-bit ARM — см.
  rknn_api.h). Изначально i32 в обёртке → порча стека → SIGSEGV внутри
  rknn_init. Решение: `#[cfg(target_arch="arm")] u32, else u64`.
- **2. Вход модели NHWC**, а не NCHW: rknn_set_input_shapes(1,1088,1088,3)
  означает dims[1]=H, dims[2]=W. Понимать по attr.fmt (RKNN_TENSOR_NHWC),
  иначе — «error code -2» и перепутанные ширрина/высота.
- **3. Никаких ручных padding в структурах**: rknn_output с ручными _pad
  сдвигал buf/size (repr(C) сам выравнивает) → «output index(-1573789832)
  out of range(9)». Ручные паддинги допустимы только там, где в C-хедере
  они объявлены явно (rknn_input).
- **Дополнительно:** выходы — NCHW (dims[1] = каналы): у YOLOv8-веток bkb
  число классов = cls_dims[1]; чтение dims[2] (=H) даёт панику индекса.

## ADR-008: Устойчивость захвата V4L2 (poll + реинициализация + сигналы)

- **Статус:** принято (2026-09-01)
- **Контекст:** камера Arducam (UVC 0c45:6366) зависала в VIDIOC_DQBUF после:
  (а) USB autosuspend, (б) грязного убийства процесса — UVC-драйвер оставался
  в состоянии стрима и не отвечал следующему open().
- **Решение:**
  1. poll(2 c) перед каждым DQBUF; таймаут → до 5 попыток полного цикла
     закрытие/открытие устройства с паузой 1 с (в потоке захвата);
  2. udev-правило `/etc/udev/rules.d/99-arducam-no-suspend.rules` —
     отключён autosuspend для 0c45:6366;
  3. обработчики SIGINT/SIGTERM (AtomicBool) + таймаут 500 мс на recv в
     главном потоке — корректный STOP не вешает процесс на заблокированном
     DQBUF мёртвой камеры.
- **Дополнение (soak-тест):** `let _ = sender;` **не закрывает канал**
  (паттерн `_` не двигает place-expression) — main висел в join() на
  воркере детектора. Явные `drop()` обоих концов канала до join.

## ADR-009: Наблюдение за OSD — MJPEG-over-HTTP на чистом Rust

- **Статус:** принято (2026-09-02, фаза B)
- **Контекст:** нужен живой просмотр работы системы с ПК. Варианты:
  GStreamer mpph264enc + RTSP (тянет gst-зависимости и сабпроцесс C),
  MJPEG-over-HTTP на std (байтрейт выше, зато ноль зависимостей).
- **Решение:** крейт `streaming` — TcpListener + multipart/x-mixed-replace,
  готовые JPEG от отдельного потока-энкодера (кодирование только при
  зрителях, семантика «свежий кадр выигрывает»). H.264/mpph264enc проверен
  (B0) и отложен до Wi-Fi/удалённого доступа.
- **Результаты:** 15.3 FPS / 3.3 Мбит/с к зрителю, просадка пайплайна 0.1 FPS.
- **Особенность железа (см. HARDWARE_TEST_RESULTS §8.2):** при
  инициализированном NPU новые входящие TCP к пользовательским листенерам
  борта не проходят (sshd/systemd — проходит). Готовы два пути:
  1. **Push-режим (основной):** борт сам подключается к зрителю исходящим
     TCP (`--stream-push <ip>:9000`, `streaming::MjpegPusher` с
     автопереподключением каждые 3 с; приёмник `tools/viewer.py` — zero-deps
     python, раздаёт в браузер `http://127.0.0.1:9001/`). Проверено на
     железе: 16 FPS / ~5 Мбит/с при 31.9 FPS пайплайна с живой детекцией.
  2. SSH-туннель (`ssh -N -L 8080:127.0.0.1:43117`) — резерв; на Windows
     без `-f` (форк умирает вместе с сессией).

## ADR-010: Бэкенд трекера за трейтом TrackerNets (tract | rknn)

- **Статус:** принято (2026-09-02, фаза C)
- **Контекст:** для наведения без стабилизации нужен трекинг <10 мс/кадр
  (бюджет 16.7 мс при 60 FPS); tract на CPU давал 30.3 мс.
- **Решение:** `nano_track::TrackerNets` — трейт нейро-бэкенда (кропы Img →
  фичи zf/xf → cls/bbox). Реализации: `backend_tract` (CPU, везде) и
  `backend_rknn` (фича npu, только борт). Выбор — `tracker.backend` в конфиге.
- **Модели:** tools/convert_nanotrack.py — backbone 127/255 int8
  (mmse + per-channel), голова int8. Калибровка — 150 живых кадров камеры,
  zf/xf для головы через onnxruntime.
- **Результаты (борт):** track 30.3 → **6.21 мс**, пайплайн **59.9 FPS**
  (640×480@60), score идентичен tract (0.881), 100% TRACKING.

## ADR-011: Триquirk'а librknnrt 2.3.0, пойманные диагностикой --diag-nets

- **Статус:** принято (2026-09-02)
- **1. Float-входы мульти-входовых графов ждёт в NHWC** даже при
  attr.fmt=NCHW (голова): NCHW-кормление давало cls cos 0.89 против tract,
  NHWC — 0.993/0.9996. Симулятор x86 при этом честен к NCHW — расхождение
  только на устройстве. Лечение: nchw_to_nhwc перед подачей (backend_rknn).
- **2. optimization_level=3 портит численику этой сети** при fp16-конвертации
  (агрессивный fusion): голова opt=3 давала cos 0.90 даже в симуляторе,
  opt=1 — 1.00000. Конвертируем с opt=1.
- **3. fp16-граф головы исполняется на устройстве с потерей точности**
  (симулятор 1.000, устройство 0.89 — независимо от opt). Голова
  сконвертирована в int8 mmse — на устройстве верна (0.993+).
- **Диагностика:** `synergy --diag-nets` — косинусная близость выходов
  tract↔rknn на одинаковых кропах, включая проверку layout (raw/perm).

## ADR-012: Коммандер наведения — порт протокола и закона bkb (фаза D)

- **Статус:** принято (2026-09-02)
- **Протокол (из bkb `utils/uart_translator.py`):** MSP v1 (Betaflight/INAV)
  поверх UART 115200 8N1, 30 Гц. Основное сообщение SET_RAW_RC (200):
  `$M< <len> <cmd> <16×u16 LE мкс> <crc8-XOR>`; ARM — MSP2_SET_ARMING
  (`$M< 03 23 03 01 crc`, crc по всем байтам — особенность bkb);
  телеметрия — MSP_RAW_GPS (106) `$M>` ответ.
- **Закон (из bkb `utils/shim.py`, без легаси-эвристик):** нормированная
  ошибка (цель − центр кадра), мёртвая зона px, PID с анти-виндапом,
  slew-лимит мкс/тик, свап осей (камера 90°) и реверсы — в конфиге.
- **Крейт `commander`:** msp.rs (кодек + golden-тесты), law.rs (закон),
  sim.rs (PlatformSim: инерция 1-го порядка + AimLink trait), uart.rs
  (serialport-rs — чистый Rust, ADR-001).
- **Валидация:** замкнутый контур на симуляторе — статичная цель
  сходится в ±30 px без автоколебаний; движущаяся (Лиссажу) — медиана
  ошибки < 30 px после захвата. На борту: 60 FPS пайплайна с активным
  коммандером, 422 RC-кадра/20 с, без просадки.
- **До железа:** включить UART в device-tree борта (overlay), подключить
  полётник, тюнить kp/kd. Нет устройства → NoopLink с WARN (не падаем).
- **NPU-ядра разведены:** детектор — core 0, трекер — core 1
  (RknnModel::load_on_core).

## ADR-013: Цифровая стабилизация GMC для жёсткого монтажа камеры

- **Статус:** принято (2026-09-03, ночная смена)
- **Контекст:** камера без виброразвязки/гимбла — глобальная тряска кадра
  сбивает трекер (поиск NanoTrack ±64 px).
- **Решение:** `nano_track::gmc::GmcEstimator` — прореживание 8× (640×480 →
  80×60 grayscale, box-фильтр), SSD-поиск сдвига ±4 малых px (±32 полных)
  с субпиксельной параболой; HybridTracker сдвигает позицию цели оценкой
  до update(). Включается `pipeline.gmc` (по умолчанию выкл).
- **A/B на борту (синтетика, тряска 60 px, NPU-трекер):** потерь 2 против 5,
  латентность ре-захвата 66 против 101 мс, score-min 0.74 против 0.63;
  стоимость < 0.5 мс/кадр. При 25 px оба режима держат 100% — GMC включать
  при заметной тряске (полевые испытания покажут).
- **Ограничение:** окно оценки ±32 px/кадр; сильнее — трекер всё равно
  теряет (ре-захват выручает: 19 мс в LOST-режиме).

## ADR-014: COCO-фолбэк-детектор — путь работает, int8-качество нет

- **Статус:** ОТКЛЮЧЕНО решением заказчика (2026-09-03); код и модель
  сохранены (декодер SingleHead, tools/convert_detector.py,
  models/yolov8n_coco.rknn), в app — предупреждающий WARN при
  SingleHead-модели; включение — явной заменой detector.model_path.
- **Что сделано:** yolov8n.onnx → RKNN (tools/convert_detector.py, 120 кадров
  калибровки); декодер SingleHead [1,84,8400] на борту работает (80 классов),
  полный путь детекции валидирован; rknn-sys: set_input_shapes только для
  динамических моделей (статические падали — фикс).
- **Проблема:** единый выход [1,84,8400] квантуется per-tensor — cls-логиты
  теряются на фоне bbox-диапазона: все conf ровно 0.500, тысячи вырожденных
  боксов; инференс 136 мс (против 32 у bkb 9-веточной).
- **Вывод:** фолбэк требует 9-веточного экспорта COCO-модели (как bkb
  model_5 — cls/box раздельно). Инструменты и пайплайн готовы, модель —
  в бэклог (нужен экспорт yolov8 с раздельными выходами).

## ADR-015: gst-конвейер H.264 на vendor-сборке — триquirk'а

- jpegparse/jpegdec не выдают кадры ни из fdsrc, ни из filesrc (пустой
  вывод, EOS сразу) — JPEG-путь gst непригоден; решение: сырой NV12 через
  rawvideoparse (format=nv12 в нижнем регистре, use-sink-caps=false).
- `filesink location=...` обязан быть ОТДЕЛЬНЫМ argv-токеном (иначе
  «syntax error» при exec-запуске, но не из шелла).
- mpph264enc: свойство `bps=`, не `bitrate=`.

## ADR-016: Операторское приложение (egui) и канал управления

- **Статус:** принято (2026-09-03, фаза U)
- **Решения заказчика:** нативное Rust-приложение (egui); захват первичной
  сигнатуры — двойной клик (ROI ~100px, без детекции); v1 включает
  кнопки АРМ/СТОП наведения.
- **Транспорт:** оба канала — ИСХОДЯЩИЕ от борта (quirk ядра, ADR-009):
  видео — существующий push MJPEG (:9000), управление — новый JSON-строки
  (:9010). Борт реконнектится каждые 3 с; UI — приёмник.
- **Протокол:** lock/arm/stop/ping от UI; status каждый кадр от борта
  (mode/score/fps/e2e/box/dets/armed).
- **Безопасность:** CommanderCtx.armed — RC-команды идут только при АРМ;
  разарм шлёт центры. Fail-safe на борту: обрыв контроль-канала или
  тишина UI >1 c при armed → автоматический СТОП. UI пингует 300 мс.
- **`crates/operator-ui`** (eframe/egui + jpeg-decoder): видео-текстура с
  оверлеями (детекции красным, цель цветом режима, перекрестие), двойной
  клик → LOCK с трансформом letterbox-координат, АРМ с подтверждением,
  большая кнопка СТОП, индикаторы связи и FPS.
- **Проверено на связке:** борт подключается по обоим каналам, статусы
  текут (171/12 с), lock через канал переводит в TRACK на ROI, arm/stop
  управляют armed.

## ADR-017: Система логирования battle/diag (дополнение)

- **L6 telemetry_report.py v2:** сводка по каталогу прогона (сессия/гит-хеш,
  режимы, тайминги p95, гистограмма сырых conf с рекомендацией порога по
  разрыву распределения, вибропрофиль GMC, статистика контура наведения
  RMS, здоровье RSS/SoC) + режим `--compare run1 run2` с процентами дельт.
- **L7 --replay:** оффлайн-прогон записи .mjpg (--record) через весь
  пайплайн с темпом записи (30 FPS × rate, 0 = макс. скорость); на борту —
  с реальным NPU-детектором, на ПК — tract + ручной захват. Проверено:
  запись 573 кадров → replay 287, 100% TRACKING, score 0.877.
- Особенность bkb-модели: conf = клампнутый логит, фон жёстко 0.0 —
  сырой лог наполняется только значимыми откликами (для выбора порога
  это и нужно).

## ADR-018: Сбойный режим камеры «кадр 3×3» — детект, авто-восстановление, detile-фолбэк

- **Феномен (2026-09-02/03):** UVC-камера (Arducam OV9782, 0c45:6366) периодически
  отдаёт кадр правильного размера 640×480, но содержимое — реплика одной сцены
  3×3. Подтверждено попиксельной проверкой периодичности (яркие точки
  копируются с шагом 213×160 во всех 9 тайлах, совпадение 98-99%).
- **Аппаратный уровень:** залипание переживает перезапуск процесса, systemd,
  полный ребут борта (USB-питание не снимается), unbind/bind драйвера,
  authorized-toggle, USBDEVFS_RESET, перезагрузку модуля uvcvideo и смену
  разрешения/формата (640×480 и 1280×720, MJPG). Лечится только физическим
  пересоединением USB или полным обесточиванием. Первое срабатывание ранее
  наблюдалось после быстрого re-open UVC — вероятно, триггер в firmware.
- **Калибровка детектора:** реальный сбойный кадр даёт mean_diff ≈ 11.6
  (тайлы — копии с небольшим яркостным смещением на тайл), живая сцена той
  же камеры — ≈ 85. Порог поднят с 6.0 до 30.0 (TILED_MEAN_DIFF_LIMIT);
  сцены без текстуры (std < 12) не оцениваются в принципе (слепая зона:
  тёмная комната; при появлении света детект само-включается).
- **Защита в три этажа (crates/app/src/main.rs):**
  1) валидация первого кадра на старте (open_validated_camera): до 3 попыток
     с паузой 3 с, перед второй — USB reset через tools/usb_camera_reset.sh
     (единственный root-вызов борта, sudoers NOPASSWD; сброс только интерфейса
     video0 либо authorized-toggle всего устройства);
  2) периодическая проверка каждые 150 кадров с подтверждением 3 кадрами
     подряд → восстановление посреди потока;
  3) аварийный режим **detile3x**: если камера застряла намертво — левый
     верхний тайл растягивается на весь кадр (nearest ×3): оператор получает
     цельную картинку с ~3× зумом вместо 9 копий, пайплайн продолжает работать
     (FOV сужается в 3 раза — в логе ERROR при включении).
- **Кросс-сборка (сопутствующий фикс):** WSL Ubuntu 24.04 линкуется против
  sysroot glibc 2.39, а борт — Debian 12 (2.36); Rust std тянет слабые
  pidfd_spawnp/pidfd_getpid с версией GLIBC_2.39 → «version not found».
  tools/strip_glibc_verneed.py вырезает Vernaux-записи новее 2.36 и
  переводит затронутые символы в *global* (std откатывается на posix_spawn);
  шаг встроен в tools/deploy.sh после strip.

## ADR-018-a: Коррекция первопричины «сетки 3×3» — энкодер, а не камеры

- **2026-09-04 найдена настоящая первопричина:** `encode_jpeg_bytes` упаковывала
  кадр ПЛАНАРНО (RR..GG..BB), а энкодеру (`jpeg_encoder`, `ColorType::Rgb`)
  отдавалась как ИНТЕРЛИВЕД. Энкодер читал планарный буфер построчно:
  каждый выходной пиксель = 3 последовательных байта плоскости → строка
  кадра превращалась в три стоящие рядом сжатые строки плоскости (для
  естественной сцены — три почти одинаковые копии), а три плоскости R/G/B
  давали то же по вертикали = характерная сетка 3×3 НА ЛЮБОЙ КАМЕРЕ.
- **Все камеры были невиновны.** Проверено перекрёстно: сырой захват
  v4l2-ctl с PS Eye в обход всего ПО — чистый (mean_diff 35, корреляция
  0.04–0.23); стартовый гвард борта (до энкодера) всегда говорил clean;
  «залипание, переживающее ребюты и USB-ресеты» Arducam — артефакт того,
  что баг жил в кодировщике стрима, а не в железе.
- **Фикс:** передавать энкодеру интерливед-буфер напрямую (заодно убран
  лишний full-frame пермут на каждый кадр).
- Защита из ADR-018 (гарды/детект/авто-восстановление/detile) ОСТАЕТСЯ как
  defense-in-depth на случай реальных отказов камер. Детект усилен вторым
  критерием — корреляцией девятых (> 0.85 у реплики): калибровка PS Eye
  (GRBG) дала чистую сцену mean_diff 34.5 — близко к порогу 30, одного
  mean_diff мало (защита от ложного detile на гладких сценах).
