# Соответствие принципам безопасности: аудит программного обеспечения

Дата: 2026-09-04. Проверяемый принцип (формулировка заказчика): *число
ступеней безопасности зависит от того, кто управляет: компьютер — 3,
кооперативно (человек над контуром) — 2, человек — 1.*

## 1. Найденные нормы и принципы

Прямой нормы «3/2/1 по автономности» в одном ГОСТе нет — это синтез двух
общепринятых каркасов:

1. **Принцип независимых ингибитов (independent inhibits)** — аэрокосмическая
   практика диапазонной безопасности: при доступе персонала к опасной системе
   минимум **два независимых ингибита**; для катастрофических опасностей
   (пиротехника, система уничтожения) — **три независимых ингибита**
   (двухотказоустойчивость). NASA Range Safety Manual (RSM 2002, §5.1),
   GSFC-STD-8009, RCC 319. Ключевое требование — **независимость** (нет общего
   отказа: разные каналы, питание, физика).
2. **Уровни автономности / участия человека** — HITL (человек в контуре,
   одобряет каждое действие), HOTL (человек над контуром, наблюдает и может
   вмешаться), HOOTL (вне контура). Российская формализация уровней автономности
   сервисных роботов — **ГОСТ Р 60.6.0.1-2021** (термины: телекомандный /
   автоматизированный / автономный режимы). Логика: чем меньше человек — тем
   больше барьеров должен внести конструктор.

Смежные нормы, по которым проверен софт:

- **ГОСТ Р ИСО 13850 / МЭК 60204-1** — категории останова: 0 (немедленное
  снятие питания), 1 (управляемый останов → снятие питания), 2 (управляемый
  останов с сохранением питания). Аварийный останов — только категории 0 или 1.
- **ГОСТ ISO 13849-1** — элементы систем управления, связанные с
  безопасностью: категории архитектур B/1/2/3/4 и уровни PL a–e.
- **ГОСТ Р МЭК 61508** — функциональная безопасность: SIL 1–4; для непрерывного
  режима / высокой частоты запросов нормируется PFH (частота опасных отказов в
  час). Контур наведения при `armed=true` работает именно в непрерывном режиме.
- **ГОСТ Р 60.1.2.2-2016/ИСО 10218-2** (интеграция робототехнических систем) и
  **ГОСТ Р 60.1.2.3-2021/ISO/TS 15066** (коллаборативные режимы) — требования к
  цепям безопасности при совместной работе человека и машины.

## 2. Режимы системы и карта автономности

| Режим synergy | Кто действует | Аналог | Требуемые ступени |
|---|---|---|---|
| `armed=false` (дежурство, просмотр, LOCK) | Человек | HITL, ручной | 1 |
| `armed=true`, оператор наблюдает, СТОП под рукой | Человек над контуром | HOTL, кооперативный | 2 |
| `armed=true`, оператор отошёл (окно закрыто/канал жив) | Компьютер | HOOTL, автоматический | 3 |

## 3. Инвентаризация барьеров (по коду)

Безопасное состояние системы: **стики в центре (RC 1500) + разарм + отсутствие
потока RC**. Определено в `commander/src/law.rs::lost()` (центры всех 16
каналов) и `main.rs::CommanderCtx` (`!armed → такт молчит`, разовая посылка
центров при разарме).

| # | Барьер | Где | Независимость |
|---|---|---|---|
| B1 | Разарм по умолчанию: `armed=false` после старта/рестарта (AtomicBool в памяти, не персистит) | `control.rs`, `main.rs` | Процесс борта |
| B2 | ARM — двухступенчатое включение (кнопка → «точно?») | `operator-ui/src/main.rs` | Процесс UI |
| B3 | Dead-man: ping каждые 300 мс; тишина > 1 с при `armed` → авто-СТОП | `control.rs:94-104`, UI `net.rs:250` | Поток канала борта |
| B4 | Обрыв TCP при `armed` → авто-СТОП | `control.rs:115-120` | Поток канала борта |
| B5 | Потеря цели (`Lost`/`Acquire`) → стики в центры каждый такт | `main.rs` tick → `law.lost()` | Главный цикл борта |
| B6 | Амплитудные ограничения: slew-rate PWM, кламп интегратора ±0.2, диапазон 1000–2000, stick_rate_px_s | `law.rs:75-83` | Главный цикл борта |
| B7 | СТОП оператора (большая кнопка): центры + разарм | UI → `emergency_stop()` | UI + главный цикл |
| B8 | Failsave приёмника полётника (RC-timeout) | **вне нашего софта** | Единственный внешний барьер |

## 4. Вердикт по режимам

### 4.1 Ручной (человек) — требуется 1 ступень: **СООТВЕТСТВУЕТ**

Без `armed` борт не формирует управление вообще (B1); RC-поток молчит; ошибка
одним кликом LOCK не создаёт движения. Одна ступень (безопасное состояние по
умолчанию) есть.

### 4.2 Кооперативный (человек над контуром) — требуется 2 ступени: **ЧАСТИЧНО**

По числу барьеров всё есть (B2+B3+B5+B6+B7 — пять). Проблема —
**независимость**: B3/B4 живут в потоке канала, но исполняются через слот
команды, который читает главный цикл (шаг 0 `process_frame`); B5/B6/B7 — в том
же процессе, на том же SoC, в том же сетевом стеке. Отказ, общий для главного
цикла и канала (зависание процесса, паника ОС, потеря питания борта), снимает
все программные барьеры разом — они считаются **одной** цепью. Второй
независимой цепью может быть только B8 (failsave полётника) — **она не входит
в наш софт и должна быть настроена на стороне полётника**.

Итог: формально 2 независимые ступени достигаются парой
«программная цепь борта + failsave полётника». Без настройки failsave — 1.

### 4.3 Автоматический (человек вне контура) — требуется 3 ступени: **НЕ СООТВЕТСТВУЕТ**

Критический сценарий, найденный аудитом (общий отказ программной цепи):

- При зависании главного цикла (например, блокирующий вызов NPU) при
  `armed=true`: `process_frame` не вызывается → RC-поток **прерывается, последний
  сигнал остаётся в силе**; B3 честно кладёт СТОП в слот команды, но читать его
  некому; commander/MSP не имеет фонового потока (`crates/commander` — нет
  `thread::spawn`). Единственная защита — RC-timeout полётника (B8).
- В `synergy.service` нет `WatchdogSec`/`sd_notify` — сторожа на зависание
  процесса нет.
- Нет аппаратного ингибита (физического выключателя цепи наведения).
- Нет аутентификации канала: любой хост в LAN может послать `{"t":"arm","on":true}`.
- `armed=true` сохраняется при потере трека (B5 даёт центры — движения нет, но
  разрешение висит до вмешательства).

## 5. Соответствие смежным нормам

- **Категории останова (ГОСТ Р ИСО 13850 / МЭК 60204-1):** наш СТОП —
  управляемый останов с сохранением питания = **категория 2**. Это легитимный
  *рабочий* останов; **аварийным остановом** (требуются категории 0/1:
  снятие энергии) он не является. Аварийный останов должен быть аппаратным
  (рубильник питания наведения), вне нашего софта.
- **ГОСТ ISO 13849-1 (категории архитектур):** цепь «dead-man + Lost→центры +
  rate-ограничения» ближе всего к **категории 2** (периодическая проверка
  liveness, реакция на обнаруженный отказ — безопасное состояние). Заявить
  уровень PL нельзя без MTTFd-данных компонентов — корректно позиционировать
  как «проектирование по принципам», не как сертифицированную цепь.
- **ГОСТ Р МЭК 61508:** непрерывный режим контура требует нормировать PFH;
  количественной вероятностной оценки у нас нет (и для исследовательского
  образца не планируется) — SIL не заявляем.
- **ГОСТ Р 60.6.0.1-2021 (уровни автономности):** текущий дизайн —
  автоматизированный (супервизорный) режим; полностью автономный режим
  (HOOTL) системой **не заявляется** и по барьерам не обеспечен.

## 6. Рекомендации (по приоритету)

1. **Настроить failsave полётника** (потеря RC → центры/нейтраль). Единственная
   действительно независимая вторая ступень; закрывает худший сценарий
   (зависание борта при armed). Делается на стороне полётника, в нашем софте —
   только документирование процедуры.
2. **systemd-сторож**: `WatchdogSec=5` + `sd_notify(WATCHDOG_1)` в главном
   цикле → зависание процесса = перезапуск = безопасный старт (armed=false).
   Дешёвая независимая (от нашего кода) третья ступень.
3. **Аутентификация канала**: общий токен в `hello` и командах (`"auth":"..."`),
   отвергать чужие. Закрывает чужой `arm` из LAN.
4. **Авто-разарм**: при `Lost` дольше N секунд при `armed` → разарм (сейчас
   центры есть, разрешение висит).
5. **Аппаратный E-Stop** (питание цепи наведения) — категория 0/1 по
   ГОСТ Р ИСО 13850; выносится за пределы ПО.
6. Диагностический журнал переходов (armed/fail-safe/LOST-таймауты) как
   отдельные события diag-режима — для разборов инцидентов (сейчас armed виден
   в commander_tick каждого такта).
