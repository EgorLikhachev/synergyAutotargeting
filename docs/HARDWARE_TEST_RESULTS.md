# Результаты тестирования на целевом железе (RK3588S)

**Дата:** 2026-09-01 · **Устройство:** Radxa ROCK 5A v1.2 (`radxa@192.168.0.224`)
**SoC:** RK3588S, 4× Cortex-A76 + 4× Cortex-A55, 16GB RAM, NPU 6 TOPS
**NPU runtime:** librknnrt.so **2.3.0** (apt `rknpu2-rk3588`)
**Kernel:** 6.1.84-8-rk2410 (Radxa Debian 12 bookworm)
**Камера:** Arducam USB (UVC `0c45:6366`, OV9782), MJPG 640×480@30
**Код:** synergyAutotargeting main @ 77053e1 · все крейты — Rust

Этот документ — living-запись первого полного прогона гибрида (вариант C)
на реальном NPU-железе. См. также [SDD-SPEC.md](SDD-SPEC.md) и
[decisions.md](sdd/decisions.md) (ADR-006…008 родились из этого прогона).

**Радикальное отличие от Autotargeting:** инференс идёт **in-process через
Rust-FFI** (35.7 мс на кадр 640×640), а не через C++ bridge по Unix-сокету
с base64 (там было 96 мс раунд-трип, потолок ~10 FPS детекции). C++ в рантайме
больше не участвует вообще — ADR-001 выполнен буквально.

## 2. Конфигурация стенда

- Захват: `capture::v4l2_direct` — ioctl без посредников, MJPG → RGB24,
  6 буферов MMAP, poll(2 с) + до 5 реинициализаций устройства при таймауте.
- Детектор: `models/model_5_dynamic_rk3588.rknn` (bkb; вход [1,?,?,3] UINT8
  NHWC → 640×640; 9 выходов = 3 ветки × (box DFL[64], cls[1], сумма));
  порог 0.45; поток-воркер со `sync_channel(1)` — NPU не блокирует трекинг.
- Трекер: NanoTrack на tract: `nanotrack_backbone_127.onnx` (шаблон),
  `nanotrack_backbone_sim.onnx` (поиск 255), `nanotrack_head_sim.onnx`;
  параметры OpenCV 1:1 (lr 0.37, windowInfluence 0.455, penaltyK 0.055).
- Гибрид: `detect_every_n=10`, `iou_confirm=0.3`, `min_track_score=0.30`,
  `lost_patience=3`.

## 3. Реальные цифры с железа

### 3.1 Захват (M2)

```
MJPG 640×480@30, DQBUF-цикл: устойчивые ~31 FPS (камера выдаёт 30,
пики 31 — от джиттера меток времени)
```

Грабли, которые пришлось закрыть (ADR-008): USB autosuspend подвешивал
камеру в DQBUF; грязно убитый процесс оставлял UVC-драйвер в состоянии
стрима, следующий open() вис. Фикс: udev-правило + poll(2 с) +
полная реинициализация устройства + SIGTERM-обработчики.

### 3.2 NPU-инференс через rknn-sys (M3)

Прогон на живой камере (60 с, каждый кадр в детектор):

| Метрика | Значение | KPI-цель (SDD §15) |
|---|---|---|
| infer 640×640 (copy-mode, want_float) | **35.7 мс** | < 60 мс ✅ |
| теоретический потолок NPU-детекции | ~28 FPS | — |
| фактическая частота детекции в гибриде | каждые 10 кадров (~2.8/с) | — |

Подтверждение на финальном бинаре (2f3792c, `--duration 60`, без demo):
1887 кадров, **31.4 FPS** (пайплайн не отстаёт от камеры даже при 787
инференсах — ~13 Гц NPU в параллельном потоке), средний инференс 35.8 мс,
самостоятельный выход с кодом 0.

Zero-copy (rknn_set_io_mem) на этой сборке рантайма падает SIGSEGV в
DRM-ioctl'ах (ADR-006, strace в docs/syn.strace.txt) — copy-mode не узкое
место: 35.7 мс доминирует NPU-прогон, а не копирование буферов.

### 3.3 Трекер NanoTrack на борту (M4)

```
track = ~30.3 мс/кадр (backbone255 + head + препроцессинг, tract release)
при бюджете кадра 33.3 мс (30 FPS) — трекер является узким местом пайплайна
```

### 3.4 Гибрид C end-to-end (M5, прогон run7)

```
кадров: 1132 (40 с), FPS: 28.3
детекций: 114 (все с целью), реинициализаций трекера: 114
средний track: 30.26 мс
кадров в TRACKING: 1132 (100%), в LOST: 0
```

Телеметрия (последние строки): стабильный бокс `x≈274 y≈177 w≈112 h≈135`,
score 0.796, fps 28.8. Снапшоты с OSD — docs/img/.

> **Примечание к цифре 114/1132:** в этой конфигурации детектор работает в
> режиме `--demo-detect` (фабрика центрального бокса): 1-классовая модель
> bkb в комнатной сцене без целевого объекта даёт 0 срабатываний (§5), поэтому
> для валидации трекера на реальных кадрах цель подменялась. Каждый
> «handoff» детекция→реинициализация→трекинг отработал на живом видеопотоке.

## 4. Soak-тест (M6)

Прогон `--duration 330 --demo-detect` (5.5 минут непрерывно, коммит 77053e1 +
фикс shutdown):

```
кадров: 9488 (обработано), FPS: 28.7, длительность: 330.0s
камера выдала: 10516 кадров (31.9 FPS) — ~10% отброшено ограниченным каналом
  (backpressure: обработка 30.5 мс против 31.3 мс интервалом кадра)
детекций: 993 (с целью: 993), реинициализаций трекера: 993
средний track: 30.47 мс, кадров в TRACKING: 9483 (100%), в LOST: 5
```

Телеметрия (9488 строк, python-агрегаты по JSONL):

| Метрика | Значение |
|---|---|
| score трекера min / median / max | 0.780 / 0.809 / 0.845 |
| track_ms median / p95 | 30.2 / 30.8 (деградации нет от начала к концу) |
| fps median / max | 28 / 30 |
| бокс x ∈ [213, 354], w ∈ [109, 129] | цель-фантом в центре 320, трекер его держит |

Ошибок в логе 0 (grep по timeout/error/panic/реинициализация — пусто);
снапшоты писались каждые 30 кадров (316 файлов). «Средний инференс NPU 1.0 мс»
в этом режиме — время фабрики фантом-детекции, реальный NPU-инференс — §3.2.

**Найден и закрыт баг shutdown:** после итоговой статистики процесс не выходил
(gdb: воркер npu-detector в `recv()`, main в `join()`). Причина —
`let _ = det_req_tx;` **не роняет канал**: паттерн `_` не двигает
place-expression (проверено изолированным тестом — висит так же). Фикс:
явные `drop(det_req_tx); drop(det_resp_rx);` до `join()`.

Верификация путей завершения (после фикса):

| Сценарий | Результат |
|---|---|
| естественное завершение (--duration 30) | сам вышел, `EXIT_CODE=0`, ИТОГ напечатан |
| SIGTERM посреди прогона | graceful за ~1.0 с: «получен сигнал остановки» → ИТОГ → выход |
| 330 с непрерывно | 0 реинициализаций камеры, 0 утечек кадров в телеметрии |

## 5. Ограничение: класс-набор модели

`model_5_dynamic_rk3588.rknn` из bkb — **одноклассовая** (cls-голова [1,1,G,G]):
единственный класс — целевой объект bkb. В офисной сцене такого объекта нет →
0 детекций за 60 с при 627 инференсах (все ниже порога 0.45). Референс-проверка
той же модели через python-rknnlite на борту дала тот же результат —
декодер и FFI-путь корректны, дело в отсутствии объекта в кадре.

**Что это значит для полевых испытаний:** нужен реальный целевой объект в
кадре (или заменить .rknn на модель с нужным класс-набором — интерфейс
детектора это позволяет, layout определяется автоматически).

## 7. Грабли, найденные на железе (все закрыты)

1. **rknn_context — u64 на aarch64** (u32 только на 32-bit ARM): изначальный
   i32 в обёртке портил стек → SIGSEGV в rknn_init. ADR-007.
2. **Вход NHWC, а не NCHW**: rknn_set_input_shapes([1,640,640,3]) —
   dims[1]=H, dims[2]=W; лечится разбором по attr.fmt. ADR-007.
3. **Ручные padding в rknn_output** сдвигали buf/size → «output index(-157…)
   out of range(9)». repr(C) выравнивает сам. ADR-007.
4. **Zero-copy rknn_create_mem** → DRM GEM_FLINK EACCES → SIGSEGV внутри
   librknnrt. Перешли на copy-mode. ADR-006.
5. **USB autosuspend камеры** → DQBUF вис. udev-правило. ADR-008.
6. **Мёртвый UVC после kill -9** → следующий open() вис. poll-таймаут +
   реинициализация устройства + SIGTERM-обработчики. ADR-008.
7. **Число классов YOLOv8-выхода**: NCHW → nc = dims[1]; чтение dims[2]
   (=H=80) давало панику индекса и молчаливую смерть воркера детектора.
   Теперь воркер обёрнут в catch_unwind с ответом по каналу.
8. **`let _ = x;` не роняет значение** (паттерн `_` не двигает
   place-expression): канал детектора жил вечно → main висел в join() после
   ИТОГ. Только явный `drop(x)`. Поймано gdb-бэктрейсом на борту + изолированным
   тестом; см. §4.

### 8.2 Грабля: входящие TCP на пользовательские порты при работе synergy

**Симптом:** пока процесс synergy работает (любой режим — камера/синтетика),
новые входящие TCP-соединения с внешних хостов к пользовательским листенерам
борта (наш сервер, python http.server — любой порт) не устанавливаются
(refused/timeout, SYN до ядра не доходит — tcpdump 0 пакетов). При этом:

- ssh:22 (systemd socket activation) — работает;
- установленные соединения — работают;
- ICMP (ping) — работает, интерфейс без ошибок/drops;
- борт → сам себя (localhost и свой LAN-IP) — работает;
- **борт → наружу (новые исходящие TCP) — работает**;
- без synergy — 12/12 соединений за 60 с, стабильно.

Общий фактор всех отказов — инициализированный NPU-драйвер (rknn_init есть во
всех режимах synergy; python-тесты его не трогают). Корень не найден
(подозрение на vendor-ядро 6.1.84 + rknpu2), занесено в открытые вопросы.

**Рабочее решение №1 — push-режим (основной):** борт сам подключается к
зрителю исходящим TCP (работает всегда):

```bash
# на ПК:  python tools/viewer.py                       # приёмник :9000 + браузер :9001
# на борту: synergy --duration 0 --stream-push <ip-ПК>:9000
# смотреть: http://127.0.0.1:9001/
```

Замерено: 16 FPS / ~5 Мбит/с к зрителю при 31.9 FPS пайплайна с живой
NPU-детекцией; автопереподключение (ретрай 3 с) проверено перезапуском
приёмника.

**Решение №2 — SSH-туннель** (резерв; порт 22 и localhost борта работают
всегда): `ssh -N -L 8080:127.0.0.1:43117 radxa@192.168.0.224`, затем
`http://127.0.0.1:8080/`.

⚠️ На Windows не использовать `ssh -f`: форк кривой, процесс умирает вместе
с сессией → обрыв туннеля (поймано на практике).

### 8.3 H.264 (B2) — отложено

Аппаратный энкодер проверен и работает (`mpph264enc`, gst-rockchip; smoke:
640×480 ~1.1 Мбит/с, matroskamux; mp4mux на этой версии глючит). Не
включён в рантайм: MJPEG 3.3 Мбит/с на LAN достаточно, а просмотр всё равно
идёт через туннель. Вариант на будущее — при Wi-Fi/удалённом доступе.
