## Выводы

1. **Конвейер стабилен**: 18/18 прогонов без падений, сервис после батча
   поднялся сам. Заодно подтверждён фикс краш-лупа (см. git 2dda200).
2. **Трекер — сильная сторона.** Гибрид C умножает покрытие: трек-цель в
   5–7 раз больше дет-цель (напр. day_134930: 71 → 475 кадров). Медианная
   ошибка 7–15 px при допуске 35 px — рабочее наведение. Худшие 25–26 px
   (day_132550, day_134827, th_140209) — на грани, смотреть кейсы.
3. **Детектор — узкое место, день хуже тепловизора.** Полнота детекции
   3–8 % (цели 7×4 px, p90 16×16 — на пределе для входа 640×640).
   На дневных роликах conf попаданий и фона перекрывается
   (0.68–0.76 против 0.52–0.73) — **порог отсечки не помогает**.
   На тепловизоре разделение есть: 0.4–0.66 против 0.06–0.40 →
   рабочий порог conf_th ≈ 0.40–0.50.
4. **Практическая схема подтверждена**: авто-захват вслепую на дневном
   канале не надёжен — рабочий путь оператора: ручной LOCK двойным кликом
   (ROI ~100 px, трекер инициализируется без детекции) + удержание.
   Тепловизор может позволить авто-захват с порогом ~0.45.

## Рекомендации (по убыванию эффекта)

- R1: дообучить модель на мелких целях дня (тёмный силуэт на небе);
  аугментация «даунскейл цели до 4–16 px».
- R2:	tile/zoom-инференс (2×2 тайла по 640) для дневного канала — цель
  станет ~14×8 px в тайле; цена — ×4 NPU-нагрузка (вариант: только при
  отсутствии трека).
- R3: установить conf_th: тепловизор 0.45, день — оставить мягким,
  фильтрация через трекер (init только по ROI оператора).
- R4: разобрать кейсы ошибки > 20 px (day_132550, day_134827) —
  возможно, GT-дрейф или потеря на контрастном фоне.

## R2-эксперимент: тайл-инференс 2×2 (2026-09-08, ADR-022)

Гипотеза R2: при отсутствии трека детектировать 2×2 тайлами — цель 7×4 px
получает ×2 разрешение (~14×8). Реализовано и измерено на тех же 9 дневных
роликах (оба режима, реальный NPU, идентичный скоринг):

| метрика (сумма по 9 роликам) | база (кадр 640) | тайлы 2×2 |
|---|---|---|
| дет-цель (кадры) | **162** | 131 |
| трек-цель (кадры) | **1140** | 916 |
| дет-any (кадры) | 173 | 111 |

**Вывод: выигрыша нет** — падение по всем метрикам. Модель не обучена на
целях такого размера (×2 разрешения недостаточно), а ×4 NPU-нагрузка на
цикл (~128 мс против 32) режет частоту ре-захвата. Дефолт `tiled_lost =
false`; путь к улучшению дневного канала — R1 (дообучение с аугментацией
«даунскейл цели до 4–16 px»). Подробности и решение — ADR-022.

## R4-разбор (2026-09-09): «худшие кейсы» оказались системными

Гипотеза R4 была «разобрать 2-3 кейса ошибки >20 px (GT-дрейф?)». Разбор
по полной телеметрии показал другое: **метрика «ошибка» в основной
таблице — медиана только по кадрам В ДОПУСКЕ** (scorer appending errs
только при |err|≤35) — «медиана выжившего». Честный пересчёт по ВСЕМ
TRACK-кадрам с GT (новые колонки скorer'а `оф%` и `мед-все`):

Механика (по worst-кадрам): трекер уверенно (score 0.8–0.9) ведёт фон в
сотнях px от цели; ошибка коррелирует со скоростью GT (быстрый GT >5 px/кадр:
медиана 66–67 px против 26–43 у медленного — цель уходит, трекер остаётся);
ре-якорение не происходит, т.к. детектор попадает по цели 3–8 % кадров и
LOST-триггер (падение score) не срабатывает на уверенном фоне.

**Выводы:** (1) GT невиновен — это реальный дрейф трекера на дневном
канале; (2) «трек-цель ×5–7» из основной таблицы — верхняя оценка
полезного времени, реальное удержание 19–61 %; (3) корневой фикс — R1
(детектор, попадающий по цели, → естественный ре-якор через iou_confirm);
частичный паллиатив на.today — операторный цикл «снять захват → повторный
LOCK» при видимом дрейфе; (4) scorer обновлён честными метриками — впредь
основная таблица показывает оф% и полную медиану.
